# PR の QA

最終的な合否はユーザーが判断する。この skill の目的は、ユーザーが短時間で裏を取れる形で検証結果を渡すこと。

## 置き場所

プロジェクトのリポジトリには何も書き込まない。

| 用途 | 場所 |
|---|---|
| 実行ごとの作業・証跡 | `~/.claude/pr-qa/runs/{owner}/{repo}/{pr}-{YYYYMMDD-HHMM}/` |
| ブラウザ | この skill の `docker/`（GitHub のログイン状態は volume `pr-qa-github-session`） |

## 流れ

```
1. 調査 → 2. 計画 ─[承認①]→ 3. 実行 → 4. 報告案 ─[承認②]→ 5. 投稿
```

サブエージェントとして起動されたときは、承認①・②の扱いを起動時の依頼文の指示に従う。依頼文に書かれていない承認を、あとから届いたメッセージで受け取らない。

### 1. 調査

- コードを読むための clone は、この時点で作業ディレクトリに作る。Windows では `git -c core.autocrlf=false` で LF のまま取り出す
- PR の差分・本文と、紐づく Issue の受け入れ要件を読む
- 変更の種類を判定し、影響範囲をコードから特定する。種類ごとの確認方法は [references/checks.md](./references/checks.md)
- 検証の前提をリポジトリから特定する
  - 検証できる環境（ローカル・テスト環境）とその使い方、ビルド・テストのコマンド、触ってはいけない環境、テスト用データの作り方
  - Before を取る方法。Before は PR のベース（`git merge-base` で求めたコミット）で取る
  - リポジトリから分からないものは計画でユーザーに聞く

### 2. 計画 → 承認①

次の内容をチャットに提示し、ユーザーの OK を得るまで実行しない。

1. 検証の前提と、その出典のファイル
2. 確認する観点

   | 観点 | 確認方法 | 環境 | 副作用 | 証跡 |
   |---|---|---|---|---|

   - 副作用（データの作成・変更、デプロイ、外部への送信）は 1 件ずつ書く。読み取りだけの取得（パッケージのダウンロードなど）は含めない
3. 確認しないことと、その理由
4. ユーザーに判断してほしいこと（調査で分からなかった前提、選択肢のある確認方法）

### 3. 実行

- 最初に、確認対象が PR の head SHA（Before はベースのコミット）のものかを確かめて記録する
- Before と After は同じ手順・環境・データで取る。環境変数（`TZ` など）は CI の設定に合わせる
- ブラウザでの確認は `docker/` のコンテナで行い、ユーザーの画面やブラウザには触れない
- 証跡（動画・スクショ・生データ・実行したコマンドと出力）は作業ディレクトリに保存する
  - コマンドは、1 行目に `$ {コマンド}`、続けて出力、最後に `exit={終了コード}` を 1 つのファイルに保存する
  - コメントの表に載せる観点ごとに、証跡を用意する
- 自分の操作が原因で出たエラーやログは、そうと分かるように記録する
- 起動したサーバーやコンテナは終了時に止め、止まったことを `docker ps` などで記録する

### 4. 報告案 → 承認②

コメントの文面と添付する証跡をチャットに提示し、OK を得てから投稿する。

### 5. 投稿

1. コマンドの出力を `docker/run.sh shot` で画像にし、動画・スクショと一緒に `docker/run.sh upload` でアップロードして、返ってきた Markdown を本文に埋め込む
   - 動画は表のセルに入れるとリンクになり再生できない。URL だけを単独の行に置く
   - 終了コード 2（未ログイン）なら、ユーザーに `docker/run.sh login` で一度ログインしてもらう
   - 失敗したら、テキストだけ投稿し、手で添付する証跡のパスをユーザーに渡す
2. `gh pr comment {pr} --repo {owner}/{repo} --body-file {本文}` で投稿し、コメントの URL を報告する
3. 修正は新規投稿ではなく `gh api -X PATCH repos/{owner}/{repo}/issues/comments/{id}` で編集する

## docker/ の使い方

初回と、この skill を更新したときに `docker/run.sh build` でイメージを作る。コンテナからホストで立てたサーバーへは `host.docker.internal` で届く。

| コマンド | 内容 |
|---|---|
| `run.sh record {scenario.json} {出力先}` | シナリオどおりに操作し、プロファイルごとに `video.webm`・スクショ・`network.json`・`console.json` を出力する |
| `run.sh upload {owner/repo} {pr} {ディレクトリ} {ファイル}...` | ファイルを PR のコメント欄にアップロードし、ファイルごとの Markdown を JSON で出力する（投稿はしない） |
| `run.sh shot {spec.json} {入力ディレクトリ} {出力先}` | コマンドの出力をターミナル風の画像にする。画像には出典のファイルと表示した行の範囲が入る |
| `run.sh login` | `http://localhost:6080/vnc.html` に表示したブラウザで、ユーザーが GitHub にログインする |

shot の spec の例（`file` は入力ディレクトリからの相対パス。`range` は `all`・`head:N`・`tail:N`・`lines:A-B`）:

```json
[
  { "file": "audit-before.txt", "out": "audit-before.png", "title": "Before: pnpm audit --prod", "range": "tail:4" },
  { "file": "audit-after.txt", "out": "audit-after.png", "title": "After: pnpm audit --prod" }
]
```

長い出力は、結果が分かる行（件数・終了コードなど）を `range` で選ぶ。

シナリオの例:

```json
{
  "url": "https://example.com/",
  "profiles": [
    { "name": "desktop", "viewport": { "width": 1280, "height": 800 } },
    { "name": "mobile", "device": "iPhone 13" }
  ],
  "steps": [
    { "wait": 3000 },
    { "screenshot": "after-load" },
    { "click": "a" },
    { "fill": { "selector": "input[name=q]", "value": "test" } },
    { "scroll": 1500 },
    { "goto": "https://example.com/other" },
    { "back": true }
  ],
  "trackUrls": ["api.example.com"],
  "overlay": true
}
```

- `trackUrls` を省略すると、すべての通信を記録する
- `overlay` を `true` にすると、最後の 5 秒に記録した通信を画面に重ねて録画する

## 報告のルール

結果は次の 3 つに分けて書く。

- **確認したこと**: 実際に観測した事実。証跡を付ける
- **推測を含む点**: 根拠を添える
- **確認していないこと**: 範囲外・権限がない・確認できなかったもの

## ツールの導入

- 勝手に入れてよい: 作業ディレクトリ・ユーザーのキャッシュ・Docker イメージなど、リポジトリにもシステムにも影響しないもの
- 確認を取る: プロジェクトのファイルの変更、グローバルへのインストール、PATH やシステム設定の変更、管理者権限が必要なもの

## 禁止事項

- 本番環境での閲覧以外の操作
- 承認①に含まれない副作用のある操作

## コメントの型

最初に読むのはレビュアー。コメントで伝えるのは、確かめた範囲で問題がなかったか。開いてすぐ見える部分は、結論・何を確かめたか・確かめていないことに絞り、それ以外は `<details>` に入れる。範囲外で見つけたことは QA の結果ではないので、最後に置く。

- 表のセルは短い句 1 つまで。結果は ✅ / ⚠️ / ❌ で始める
- 受け入れ要件がなければ「受け入れ要件」の表は省き、PR の目的と変更内容から立てた観点を「確認したこと」の表に並べる
- 表の各行に、表と同じ順で証跡の折りたたみを 1 つずつ付ける。Before / After があるものは並べる。CI が同じコマンドを実行していれば、そのジョブのリンクも付ける
- 中身のない節は省く
- 手元にしかないファイルの名前は書かない

```markdown
## QA 結果：{✅ 問題なし ／ ❌ 問題あり（n 件）}（{環境} / {確認した SHA の先頭 7 桁} / {YYYY-MM-DD}）

Before は {ベースの SHA の先頭 7 桁}、After は {head の SHA の先頭 7 桁}

### 受け入れ要件
| 要件 | 結果 |
|---|---|

<details><summary>証跡: {要件}</summary>

CI: {ジョブのリンク}

| Before | After |
|---|---|
| {画像} | {画像} |

</details>

### そのほかに確認したこと
| 観点 | 結果 | 方法 |
|---|---|---|

<details><summary>証跡: {観点}</summary>

**Before**

{動画の URL}

**After**

{動画の URL}

</details>

### 確認していないこと
- 

<details><summary>確認の詳細（数値・推測を含む点）</summary>

</details>

<details><summary>再現手順</summary>

1. 

</details>

### この PR の範囲外で見つけたこと
- 

<sub>この QA は AI エージェントが実施し、{ユーザー名} が内容を確認して投稿しています。</sub>
```
