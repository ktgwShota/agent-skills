# レビューコメントの型

## ラベル（必須）

コメント冒頭に太字でラベルを1つ付ける。

- `**[MUST]**` : マージ前に対応が必須な指摘（バグ、データ破壊、セキュリティ等）
- `**[WANT]**` : 対応してもらえると嬉しい提案（可読性、簡潔さ、慣習等）
- `**[ASK]**`  : 指摘ではなく質問・確認（意図の確認、仕様の確認）

## 文面の構成

1. **ラベル**
2. **結論**: 何をどうしてほしいか。断定ではなく質問形式・提案形式で書く
   - MUST: 「〜のケースで壊れると思うので、〜に修正してもらえますか？」
   - WANT: 「〜にすると読みやすくなると思うので、ご検討いただけると嬉しいです」
   - ASK: 「ここは〜という意図で合っていますか？」
3. **理由**: なぜそうすべきか必ず書く。「〜してほしい」だけで終わらせない。
   問題が起きる場合は「どういう入力・状態のとき、何が起きるか」まで具体的に
4. **具体例（必要な場合）**: 挙動の説明が直感に反する・わかりにくい場合は
   必ず短いコード例を付ける（例: `{ ...undefined, a: 1 }` → `{ a: 1 }`）

## 書き方のルール

- **1コメント1論点**。別の論点は別コメントに分ける（提案コード付きの簡略化と
  設計方針の指摘は混ぜない）
- **指示語は位置を明示**。「外側の try」ではなく「外側の try（2行目の `try` 〜
  23行目の `catch`）」のように、行番号や範囲を添える
- 相手のコードを否定するトーンにしない。トレードオフがある場合は両案を併記して
  相手に判断を委ねる
- 日本語で書く。コード・識別子・ラベルは原文のまま

## 投稿フロー（必須）

1. コメント文面をチャットに提示し、ユーザーの OK をもらう。**確認なしで投稿しない**
2. OK 後、該当行にアンカーしたインラインコメントとして投稿する:

   ```bash
   gh api repos/{owner}/{repo}/pulls/{pr}/comments \
     -f body='...' \
     -f commit_id={head_sha} \
     -f path={file} \
     -F start_line={開始行} -F line={終了行} \
     -f start_side=RIGHT -f side=RIGHT
   ```

   - head SHA は `gh pr view {pr} --json headRefOid` で取得
   - 単一行なら `start_line` は省略
3. 投稿後は必ずコメントの URL を報告する
4. 修正依頼が来たら新規投稿ではなく `gh api -X PATCH .../pulls/comments/{id}` で編集する
