# レビューコメントの型

## ラベル

コメント冒頭に太字でラベルを1つ付ける。

- `**[MUST]**` : マージ前に対応が必須な指摘（バグ、データ破壊、セキュリティ等）
- `**[WANT]**` : できれば対応してほしい提案（可読性、簡潔さ、慣習等）
- `**[ASK]**`  : 指摘ではなく質問（意図・仕様の確認）

## 文面の構成

1. **ラベル**
2. **結論**: 何をどうしてほしいか。断定ではなく質問・提案形式で書く
   - 例（MUST）: 「〜のケースで壊れると思うので、〜に修正していただけますか？」
   - 例（WANT）: 「〜にすると読みやすくなると思うので、ご検討いただけますか？」
   - 例（ASK）: 「ここは〜という意図で合っていますか？」
3. **理由**: なぜそうすべきか必ず書く。問題が起きる場合は
   「どういう入力・状態のとき、何が起きるか」まで具体的に

## 書き方のルール

- **1コメント1論点**。別の論点は別コメントに分ける
  - 例: バグの指摘と命名の改善提案は別コメントにする
- **指示語には行番号・範囲を添える**
  - 例: 「この条件分岐」ではなく「この条件分岐（12〜18行目の `if` ブロック）」
- **相手のコードを否定するトーンにしない**
  - 例: 「この書き方はダメです」ではなく「〜の方が安全だと思いますが、いかがでしょうか？」

## 投稿フロー

1. 文面をチャットに提示し、ユーザーの OK を得てから投稿する
2. 該当行にアンカーしたインラインコメントとして投稿する:

   ```bash
   gh api repos/{owner}/{repo}/pulls/{pr}/comments \
     -f body='...' \
     -f commit_id={head_sha} \
     -f path={file} \
     -F start_line={開始行} -F line={終了行} \
     -f start_side=RIGHT -f side=RIGHT
   ```

   - head SHA: `gh pr view {pr} --json headRefOid`
   - 単一行なら `start_line` は省略
3. 投稿後はコメント URL を報告する
4. 修正は新規投稿ではなく `gh api -X PATCH .../pulls/comments/{id}` で編集する
