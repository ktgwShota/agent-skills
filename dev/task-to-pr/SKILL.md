# task-to-pr

あなた（main）は進行役。コードもテストも自分では書かない。ヒアリング、サブエージェントへの依頼、RED の確認、コミット、PR 作成、進捗ファイルの更新を行う。ツールを呼ぶ前後の一言も含め、文はすべてユーザーが使っている言語で書く。

## 置き場所

`{HOME}` は環境変数 `TASK_TO_PR_HOME`、無ければ `~/.claude/task-to-pr`。プロジェクトのリポジトリには、作業ブランチへのコミット以外は何も書き込まない。

| 用途 | 場所 |
|---|---|
| プロファイル | `{HOME}/profiles/{owner}/{repo}.md` |
| 記録先（実行ごと） | `{HOME}/runs/{owner}/{repo}/{slug}-{YYYYMMDD-HHMM}/` |
| worktree A（作業ブランチ） | `{HOME}/worktrees/{owner}/{repo}/{slug}/` |
| worktree B（実装用の一時ブランチ） | `{HOME}/worktrees/{owner}/{repo}/{slug}-impl/` |
| この skill の道具 | `${CLAUDE_SKILL_DIR}/scripts/` |

`{slug}` は作業内容を表す英小文字とハイフンの短い名前。同じ名前の worktree やブランチがあれば別の名前にする。記録先を作った後に名前を変えたときは、記録先の名前はそのままにし、進捗ファイルの「パス」に両方を書く。パスはすべて絶対パスでサブエージェントに渡す。

## サブエージェント

| 役割 | 種類 | 仕事 |
|---|---|---|
| planner | 名前が `task-to-pr-planner` で終わるもの | 完了要件ごとのテストケース、インターフェースの取り決め、実装方針、QA シナリオを作る |
| test-writer | 名前が `task-to-pr-test-writer` で終わるもの | テストを書く |
| implementer | 名前が `task-to-pr-implementer` で終わるもの | 実装を書く |
| reviewer | 名前が `task-to-pr-reviewer` で終わるもの | テスト一式・lint・型チェックを実行し、作業定義と diff を照らしてレビューする |
| qa | 名前が `task-to-pr-qa` で終わるもの | ブラウザで操作してスクショを撮り、QA シートを作る |

プラグインで入れた場合は `task-to-pr:task-to-pr-planner` のように接頭辞が付く。依頼文には、そのエージェントが読むファイルの絶対パスと、作業する worktree の絶対パス、記録先の絶対パスを必ず書く。

返答はどれも `python3 "${CLAUDE_SKILL_DIR}/scripts/save-return.py" --session ${CLAUDE_SESSION_ID} --role {役割} --out {記録先}/returns/{役割}-{n}.md` で保存する。返答を自分で打ち直したり要約したりせず、同じ内容を別の名前で保存し直さない。main の補足が要るときは別のファイルに書く。

## 人とのやり取り

- サブエージェントにも、途中の文と返答をユーザーの言語で書くよう依頼文で伝える
- 質問には必ず、あなたの推奨とその理由（コードや資料のどこから判断したか）を添える。選択肢があるときは推奨を先頭に置く。選択肢が 1 つしか無い事柄は質問にせず、作業定義や計画に書いて承認で見せる
- AskUserQuestion が使えるならそれで聞く。1 回に 4 問まで
- 使えないとき（`claude -p` での実行など）は、質問を番号付きの選択肢として本文に書き、そこでターンを終える。次のユーザーのメッセージを答えとして扱う
- ヒアリングで聞くのは、外から見える振る舞いと作業の範囲だけ。関数の分け方など、外から見えない実装の書き方は planner に決めさせ、承認のときに見せる。公開している関数（リポジトリの外から使われているもの）やライブラリでは、呼び出し側がエラーを区別できるかどうかも外から見える振る舞いなので聞く
- 「しなくてよい」という答えは作業定義の「範囲外」に書く。今の振る舞いを保つ事柄は、ユーザーの「変えない」という答えでも、あなたの推奨を受け入れたものでも、「互換性・制約」に書く。どちらも完了要件にしない。完了要件にするのは、ユーザーが「〜してはいけない」と明言したときと、チケットの受け入れ要件に書かれているときだけ

## 流れ

```
0. ヒアリング → 0'. 準備 → 1. 計画 ─[承認]→ 2. テストと実装を並行で書く → 3. RED を確かめて合流 → 4. レビュー → 5. QA → 6. Draft PR → 7. 報告
```

人の承認は 1 回だけ。承認の後は、[ライブラリの追加](#ライブラリの追加)と[止まるとき](#止まるとき)を除いて、PR の作成まで止まらずに進む。

### 0. ヒアリング

[references/work-definition.md](./references/work-definition.md) の作業定義を埋める。

- 入力は自由。チケットの URL、本文の貼り付け、口頭の説明のどれでもよい
- 読める情報源（GitHub の issue なら `gh api repos/{owner}/{repo}/issues/{番号}` とそのコメント）とコードを先に読み、足りない項目だけ質問する
- チケットに紐づく開いた PR があれば、作業の前に知らせ、新しく作るか止めるかを聞く。GitHub なら `gh pr list --state open --json number,title,closingIssuesReferences --jq ".[] | select(any(.closingIssuesReferences[]; .number == {番号}))"` で探す
- 完了要件は、テストや操作で確かめられる文になるまで聞き返す。あいまいな要件を自分で補って先に進まない
- 出力・API・ファイル形式・画面・CLI の引数を変える作業なら、誰（何）がそれを使っているかと、変えてはいけないものを必ず聞く（作業定義の「互換性・制約」）。仕様のとおりに直すだけのバグ修正や、既存のものを残して足すだけの変更で、名前・引数・形式を変えず、使う側をコードから特定できるなら、聞かずに「互換性・制約」に書いて承認で見せる
- チケットに書かれた仕様だけで完了要件が決まるときは、質問せずに準備へ進む。境目の値などあなたが足した完了要件や、隣にある別の問題（範囲外にするもの）は、作業定義に書いて承認で見せる
- 入力を区分に分ける要件（強さ・料金の段階など）を提案するときは、どの入力もちょうど 1 つの区分に当たることを確かめてから示す
- 質問を送る前に記録先を作り、[references/progress.md](./references/progress.md) の形で `progress.md` を作る

### 0'. 準備

1. 作業定義を記録先の `work-definition.md` として保存し、チェックポイント「0 ヒアリング」を取る
2. プロファイルを読む。無ければ [references/profile.md](./references/profile.md) に沿って作る。あっても、今回の対象のパッケージが載っていないときや、出典のファイルが「調べたコミット」から変わっているとき（`git diff --stat {調べたコミット} HEAD -- {出典のファイル}`）は、その部分を調べ直して直し、「調べたコミット」を今のベースにする。「調べたコミット」が無いときは、出典のファイルを今のベースで読み直してから記録する。資料同士で規則が食い違うとき（コミットの署名の有無など）は、プロファイルの「規則の食い違い」にユーザーの答えがあればそれに従う。無ければ、どちらかを選ばずに承認のときに聞く
3. 既定ブランチを fetch し、その先端（ベース）から worktree A（作業ブランチ）と worktree B（`task-to-pr/{slug}-impl`）を作る。ブランチ名はプロファイルの規則に従う。規則が無ければ、既存のブランチや PR の命名に合わせ、それも無ければ `{コミットの type}/{slug}` にする。ブランチ名は質問せず、承認のときに知らせるだけにする
4. 両方の worktree で、プロファイルの「worktree の準備」を実行する
5. テストの実行に必要な道具（言語のランタイムなど）が無いとき
   - `/run/sandbox` があればサンドボックスの中なので、入れてよい。版は CI と同じものにする（パッケージマネージャーに無ければ公式の配布物や版を指定できる仕組みを使う）。入れたものと、そのために変えた環境の設定（PATH を足したファイルなど）は、進捗ファイルの「決めたこと」とプロファイルの「実行環境」に書く。CI と同じ版を入れられなかったときは、その理由と使った版を PR の「残した注意点」に書く
   - それ以外の環境では、入れる前にユーザーに聞く
6. ベースのコミットで、プロファイルのテスト一式を実行し、`logs/base-*.txt` に保存する。CI が環境変数（`TZ` など）を設定していれば、付けた場合と付けない場合（README など開発者向けの手順どおり）の 2 通りで実行する。設定していなければ 1 回でよい。テスト結果をキャッシュする道具では、キャッシュを使わない形で実行する（Go の `-count=1` など）。落ちるテストがあれば既存の失敗として、2 通りで結果が違えば「環境に依存する既存の失敗」として進捗ファイルに書く

準備のコマンドは 1 項目ずつ分けて実行する。

### 1. 計画

planner に、作業定義・プロファイル・worktree A・記録先のパスを渡す。承認での修正も planner に直させ、main が書き換えない。承認された計画のパス（`returns/planner-{n}.md`）を進捗ファイルに書き、以降のエージェントにはそのパスを渡す。

### 承認

次をまとめて提示し、OK を得るまで先に進まない。

1. 作業定義
2. 完了要件ごとのテストケースと、インターフェースの取り決め・実装方針・影響範囲
3. テストが書けない完了要件と、その代わりの確認方法（1 つずつ、それでよいか）
4. 新しいライブラリ（1 つずつ、入れてよいか。名前・バージョン・理由・入れない場合の代案）
5. QA シナリオ（ブラウザで確かめる場合）
6. 計画が挙げた懸念と副作用・作業定義への提案、ベースで落ちていたテスト
7. プロファイルのうち、今回使うもの（準備・テスト・lint・型チェックのコマンドとその出典、ブランチ名、「不明」の項目）を本文に書き出す。パスを示すだけで済ませない
8. 資料同士で食い違い、プロファイルにまだ答えが無い規則。署名はコミットと PR 本文の両方について、1 つの質問で聞く。答えがプロファイルにある規則は聞かず、7 にどう従うかを書く
9. OK の後は、push と Draft PR の作成まで自動で進むこと

修正の指示があれば、planner に計画を直させて再提示する。OK と一緒に答えた質問で計画が変わるときは、planner に直させて進み（再提示しない）、変わった箇所を「7. 報告」に書く。

OK を得たら、資料同士で食い違っていた規則への答えを、プロファイルの「規則の食い違い」に書く（「承認で確認」などの仮の記述を置き換える）。

### 2. テストと実装を並行で書く

1. 承認されたライブラリがあれば、プロファイルの追加コマンドで worktree A に入れて単独でコミットし、worktree B を `git -C {B} reset --hard {A の HEAD}` で同じ状態にする
2. test-writer（worktree A）と implementer（worktree B）を、1 つのメッセージで同時に呼ぶ。お互いの成果物は見せない。どちらにも、作業定義・承認済みの計画・プロファイル・記録先のパスを渡す
3. どちらかが `STATUS: NEEDS_DEPENDENCY` を返したら、[ライブラリの追加](#ライブラリの追加)に従う
4. 両方の返答を受け取った時点で、チェックポイント「2 並行」を取る。合流の作業を始める前に取る

### 3. RED を確かめて合流

1. worktree A の変更が、プロファイルの「テストファイル」「テスト補助ファイル」だけであることを `git -C {A} status --porcelain` で確かめる。worktree B の変更に、テストファイル・テスト補助ファイル・依存ファイルが含まれないことも確かめる。外れたら、その担当に差し戻す
2. worktree A で、追加したテストをベースのコードに対して実行する。テストごとの結果が出る形（`pytest -rA`、`vitest --reporter=verbose` など）で実行し、1 件ずつ計画の「想定する失敗」と照らす。ファイル全体の収集エラーで新しいテストがまとめて落ちた場合や、既存のテストまで巻き込んで落ちた場合は、テストごとに確かめられる形に直すよう test-writer に差し戻す。構文エラー・準備の失敗も同じ（2 回まで）
   - コンパイル言語（Go・Java・Rust など）では、まだ無い公開シンボルを使うテストがあるとパッケージ全体がビルドエラーになる。その場合は、取り決めのシグネチャだけを持つ一時的なスタブを main が置いてテストごとの RED を確かめ、スタブはコミットせずに消す。RED のためにテストのファイル構成を変えさせない
3. RED のコミットを作り、出力を `logs/red.txt` に保存する（[ログの形式](#ログの形式)）
4. worktree B の変更をコミットし、`git -C {A} cherry-pick {B のコミット}` で RED の上に積む。ここでチェックポイント「3 合流」を取る

### 4. レビュー

1. reviewer に、作業定義・プロファイル・worktree A のパス・ベースの SHA・ログの保存先 `logs/round-{n}/` だけを渡す。計画、進捗ファイル、これまでの経緯は渡さない。毎回新しい reviewer を呼ぶ
2. 判定が NG なら、指摘を担当ごとに分けて戻す。どちらも worktree A で作業させる
   - 「実装の誤り」は implementer へ
   - reviewer が作業定義と照らして「テストの誤り」と判定したものだけ test-writer へ
   - 戻すときは、進捗ファイルの試行の履歴のうち、その担当の分を一緒に渡す
3. 担当の変更が受け持ちのファイルだけであることを確かめてコミットし、もう一度レビューする

「任意」の指摘は直させず、PR 本文に載せる。

レビューが OK になったら、テストが書けない完了要件の代わりの確認方法を main が実行し、`logs/alt-R{n}.txt` に保存する。代わりの確認がブラウザでのスクショなら QA の後に行い、QA の行・スクショの名前・目で確かめた結果は `logs/alt-R{n}-visual.md` に書く（コマンドのログには書き足さない）。同じログをコピーして使い回さない。人が行う操作の場合は実行せず、PR に手順と「未確認」を書く。サブエージェントの報告だけで「確認済み」にしない。

### 5. QA

計画に QA シナリオがあるときだけ行う。

1. qa に、作業定義・QA シナリオ・プロファイル・worktree A のパス・ベースの SHA・記録先・保存先 `qa/`・`${CLAUDE_SKILL_DIR}/scripts` の絶対パスを渡す。変更前の画面は worktree B をベースに切り替えて撮らせる
2. QA シートは `qa/qa-sheet.xlsx`。NG があれば implementer に戻し、レビューからやり直す

### 6. Draft PR

1. 作業ブランチを push する
2. プロファイルの PR テンプレートに沿って本文を書き、[references/pr-body.md](./references/pr-body.md) の欄を加える。記録先の `pr-body.md` に保存する
   - テンプレートの各欄は具体的に埋めるか「該当なし」と書く
   - チェックリストは、この実行のログで確かめた項目（テスト・lint・型チェックが通るなど）にだけチェックを付ける。人が確かめる項目には付けない。項目の一部が無い（lint が無いなど）ときは、チェックを付けずに理由を添える
   - 署名（Generated with … など）は、承認で決めた規則に従う
3. `gh pr create --draft --base {既定ブランチ} --head {作業ブランチ} --title {タイトル} --body-file {pr-body.md}`

### 7. 報告

1. `python3 "${CLAUDE_SKILL_DIR}/scripts/token-usage.py" --session ${CLAUDE_SESSION_ID} --progress {記録先}/progress.md --markdown` を実行する
2. 次を報告する
   - PR の URL
   - 足したコミット（`git log --oneline {ベース}..HEAD` の出力をそのまま）
   - 完了要件ごとの結果（PR 本文のテスト結果の表を 1 文字も変えずに）
   - QA シートのパス
   - 承認のときの答えで計画が変わった箇所
   - 既存の失敗や「任意」の指摘など、PR に残した注意点
   - 1 の出力（役割ごと・ステップごとの表）を、見出しと注記の行も含めて 1 文字も変えずに
   - 後片付けのコマンド（`git worktree remove {A}`・`git worktree remove {B}`・`git branch -D task-to-pr/{slug}-impl`）

## 進捗ファイル

書くのは main だけ。形式は [references/progress.md](./references/progress.md)。

- 行わなかったステップ（QA シナリオが無いなど）は、チェックポイントを取らない
- 各ステップの終わりに、そのステップの分だけ（複数のステップをまとめずに）「現在地」を書き換え、`python3 "${CLAUDE_SKILL_DIR}/scripts/token-usage.py" --session ${CLAUDE_SESSION_ID} --checkpoint "{ステップ名}" --progress {記録先}/progress.md` でチェックポイントを取る。時刻・経過時間・トークン使用量の累計が追記される。時刻を手で書かない
- 差し戻しのたびに、試行の履歴に 1 行足す

## ログの形式

コマンドの出力は、エージェントの要約ではなくコマンドからそのまま保存する。1 行目に作業ディレクトリ付きで `$ cd {パッケージのパス} && {コマンド}`、続けて出力、最後に `exit={終了コード}`。

```bash
{ echo "$ cd {パッケージのパス} && {コマンド}"; (cd {パッケージのパス} && {コマンド}) 2>&1; echo "exit=$?"; } > {ログのパス}
```

計測や確認のために書いたスクリプトは、記録先の `scripts/` に置き、ログからそのパスで呼ぶ。`/tmp` に置かない。

どのステップでも、長くかかりうるコマンドには `timeout` を付け、標準入力を待つ書き方（引数の無い `cat >`、`cat >> /dev/null` など）はしない。

## ライブラリの追加

エージェントも main も、承認を得ずに依存を増やさない。テストライブラリが無くてテストが書けない、バリデーションのライブラリが無くて冗長になる、といった場合も同じ。

- 計画の段階で分かったものは、承認のときに聞く
- 実装中にサブエージェントが `STATUS: NEEDS_DEPENDENCY` を返したら、その場で止まってユーザーに聞く。名前・バージョン・理由・入れない場合の代案・ライセンス・最終リリース日を添え、推奨を示す
  - OK なら main が worktree A に入れて単独でコミットし、worktree B にも反映して、同じ担当に続きを依頼する
  - 断られたら、使わずに書くよう指示して依頼し直す
  - どちらもループの回数には数えない
- テストの実行に必要な道具（ランタイム・ブラウザなど）は依存ではない。[準備](#0-準備)の 5 に従う

## 中断と再開

API の利用上限などでサブエージェントや main が途中で止まったとき、コンテキストが圧縮されたとき、会話を再開したときは、次の順で再開する。

1. 進捗ファイルを読み、済んだステップ（エージェントの呼び出し・コミット）を確かめる
2. 担当の worktree の状態を `git status` で確かめる
3. 止まったエージェントは、続きから再開できればそれを使い（SendMessage など）、できなければ途中の状態を説明して新しく呼ぶ
4. 試行の履歴に書く。差し戻しの回数には数えない

ユーザーが同じメッセージを送り直してきたときも同じ。済んだステップは繰り返さない。

## 止まるとき

- レビューと QA の差し戻しが合わせて 3 回を超えた
- RED の差し戻しが 2 回を超えた
- サブエージェントが `STATUS: BLOCKED` を返した

PR を出さずに止まり、どこで何が解決しなかったかを、最後のログやレビューの指摘とともに報告する。[7. 報告](#7-報告)の 1 の出力と、足したコミット・後片付けのコマンドも載せる。worktree とコミットは残す。

## 後片付け

この実行で起動したサーバー・コンテナは、名前やプロセス ID を進捗ファイルに書き、終了時（止まったときも含む）にそれを指定して止める。qa が起動したものは `qa/pids.txt` を見る。ユーザーの開発環境のものは止めない。
